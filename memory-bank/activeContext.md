## Active Decisions
- Near-term planning prioritizes systems and mechanics that one programmer can build and validate without new art. Defer presentation polish, broad content production, and art-dependent work until the gameplay systems are coherent.
- Do not schedule a real character-selector screen in the current gameplay roadmap; keep the isolated temporary first-character selection until the user reintroduces that scope.
- Do not schedule price, recipe, or drop-rate balancing yet. Implement correct rules and data flow first, then balance after the systems can be exercised together.
- Treat Kill quest progress as additive event history. Enemy deaths grant one Kill event to each authenticated member of the killer's current party who is within the current 1000-unit reward radius measured from the defeated enemy, or only to the killer when solo. Treat Collect quest progress as the absolute count currently present in the authoritative character inventory: accepting initializes it from existing items, every persisted add/remove resynchronizes it, and losing items may return a Finished quest to Accepted until the requirement is held again.
- An active craft is client-interrupted by movement input, actual received damage, closing/replacing its UI, or leaving the crafting-station radius. The server-side recipe/material/station validation remains separate future hardening work.
- Treat the repository as two cooperating applications:
  - `Client/`: Unity 6000.1 project using Netcode for GameObjects.
  - `API/`: ASP.NET Core API using clean/layered architecture.
- Keep code clean, understandable, and as simple as reasonably possible. Avoid unnecessary complexity and abstractions, and follow the organization, naming, style, and conventions established by the surrounding code.
- Use blank lines to expose logical blocks rather than packing independent operations together. Keep assignment targets and their right-hand expressions on one line; extract meaningful locals or separately formatted initializers when an expression is too complex, rather than breaking directly after `=`. In tests, separate fixture/service setup, scenario-specific values, actions, and assertions; consecutive async calls or exception assertions for different behaviors should each have their own visual block. Keep tightly related values and checks together so spacing communicates structure instead of becoming noise.
- In LINQ query chains, put every independent filter condition in its own `.Where(...)` call instead of combining conditions with `&&` inside one `Where`. Use `x => x...` rather than generic placeholder names such as `candidate`.
- Prefer scene-backed, reusable prefabs for Unity UI structures. Each `*UI.cs` class should resolve its owned controls from the transform hierarchy at startup and cache them in fields, following `LoginUI`, instead of exposing all child controls as serialized Inspector references. Keep serialized references for external prefab/configuration assets that are not part of the owned hierarchy. Create UI structures programmatically only when their dynamic nature justifies it, and instantiate repeated dynamic UI from prefabs rather than constructing it ad hoc.
- Treat responsiveness as a requirement for every new or modified Unity UI: use appropriate `RectTransform` anchors/stretch and layout components in the prefab, keep the `CanvasScaler` policy explicit, preserve margins on narrow screens, and verify representative landscape plus narrow/portrait proportions. Fixed pixel values may define preferred sizes, but must not be the only sizing mechanism.
- Put unchanging scene/prefab `TextMeshProUGUI` labels on `TranslateUI` with a serialized `TranslateKeyEnum` instead of assigning them once from `*UI.cs`. Continue using runtime `TranslateManager` lookups for dynamic/stateful text, names, counts, formatted values, logs, and messages. Do not put the current authenticated-user-backed `TranslateManager` on pre-login UI until locale initialization is decoupled from login, because early singleton construction would cache the default language.
- Treat a focused `TMP_InputField` as exclusive keyboard input through the shared `InputFocusUI` check. Player movement/camera controls and gameplay keyboard shortcuts must not react while any active UI input is focused.
- Keep `LoadingScene` first and loaded for the lifetime of a client session so its high-order, input-blocking Canvas can cover every additively loaded scene. Use disposable `LoadingScreenUI` scopes at orchestration boundaries instead of coupling request transport helpers to UI; dedicated-server scene order remains Bootstrap-first.
- Keep `Bootstrap` focused on application startup and API orchestration; keep login view lookup, field/loading state, validation, focus styling, and password visibility inside the scene-scoped `LoginUI` component. The visual hierarchy remains in `BootstrapLogin.prefab`, while the reusable `SpinnerUI` component owns spinner animation.
- Use persistent `MonoSingleton` behavior by default, but opt scene-owned UI such as `LoginUI` out through `PersistBetweenScenes` rather than carrying bootstrap-only objects into gameplay scenes.
- Keep login request/response types marked as sensitive, never log credentials or bearer tokens, and preserve the generic public `401` response. Identity lockout and endpoint rate limiting are required protections for the login path.
- Keep each JWT access token capped and validated at one hour and each authenticated session capped at 24 hours from its signed original `session_started_at`. Both Unity runtime roles refresh through the authenticated `ApplicationUsers/RefreshSession` endpoint after 56 real-time minutes and replace `UserManager.Token`; the API must reject refresh before the current token's final five minutes and must never move the global session deadline. Refresh does not revoke the old JWT, so it remains valid until its original expiry. Transient refresh failures retry only through the remaining four-minute client window, while terminal authorization errors, an exhausted token window, or the 24-hour deadline invalidate the session. Clients return to Bootstrap login after shutting down authenticated scenes/networking; dedicated servers exit for supervised restart. Client JWTs remain process-local and must never be sent through Netcode; delegated gameplay API work uses the server JWT plus `PlayerSessionId`. Bearer tokens must remain absent from logs. Require authenticated users by default, mark only genuinely public endpoints with `AllowAnonymous`, accept HS256 only, and reject JWT secrets shorter than 32 UTF-8 bytes during startup.
- Read all memory bank files at the start of every task, per `.Codexrules`.
- Local dev startup automation lives inside the Unity project under `Client/Automation/`, not at repository root.
- Unity menu entries under `ProjectX` should remain aligned with `Client/Automation/run.bat`.
- If `.claude/settings.local.json` reappears, treat it as local-only secret configuration and do not commit or quote it.
- Treat current character stat totals as persisted mutable values until the user clarifies whether stats should be recomputed from base stats plus gear bonuses.
- Keep ammo-consumption and zero-count unequip decisions on the Unity server. `UpdateCharacterCommand` is a persistence pass-through for the submitted `AmmoType`, `AmmoCount`, and stats and must not automatically replace ammo types or normalize ammo counts.
- Resolve character state through `UserManager.Characters[clientId]`; do not reintroduce a process-wide single `Character` reference.

Dexterity is also capped dodge chance, Speed increases movement, and Armor is capped damage reduction.

Weapon/ammo compatibility is category-based and read from `InventoryItemParametersAttribute.WeaponCategory`: Arrows/Bow, Runes/Wand, Feathers+Oils/Sword.
