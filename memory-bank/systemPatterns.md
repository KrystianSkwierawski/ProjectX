# System Patterns

## Repository And Backend Architecture
- `Client/` is the Unity client/dedicated server; `API/` is the layered .NET backend; root `AGENTS.md` defines repository instructions and documentation routing.
- Follow applicable `jasontaylordev/CleanArchitecture` dependency direction: Domain is framework-free business state, Application owns use cases/ports/validation, Infrastructure owns EF/Identity/JWT/localization/game-session adapters, and API owns transport, authorization, OpenAPI, rate limiting, and composition.
- Backend tests mirror those boundaries: Domain/Application unit, Infrastructure integration, Web acceptance, and Architecture tests. Do not add outer-layer references to inner-layer tests.
- Minimal API handlers are public/static and use typed results. Await MediatR into a local result before constructing the response; attach concise summary/description, authorization, rate limits, and non-inferred errors in route mapping.
- Operation folders keep handler/request together; validators and operation-owned DTOs have separate files. Concrete MediatR requests must define safe `ToString()` output.
- Domain entities own I/O-free invariants; Application coordinates authorization, loading, domain calls, and persistence. The authenticated Unity server owns gameplay calculations, so API character updates persist trusted supplied state rather than duplicating all gameplay rules.
- `ApiExceptionHandler` is the sole exception-to-HTTP boundary: invalid credentials `401`, forbidden `403`, validation `400`, missing resources `404`; unexpected failures remain server errors.
- API application timestamps use injected singleton `TimeProvider.GetUtcNow()`, `DateTimeOffset`, and the EF auditable interceptor. Local-time conversion belongs only to UI.
- Development-only database initialization intentionally deletes/recreates/seeds. Production and NSwag must never invoke it.

## Authentication, Sessions, And Networking
- MonoSingleton defaults to scene lifetime. UI controllers are destroyed with their canvases on startup rollback/logout and recreated on the next login; AudioManager explicitly opts into persistence across scenes.
- Authorization fails closed; only explicitly anonymous endpoints are public. JWT accepts HS256 only, requires a 32-byte secret, caps access tokens at one hour, and preserves a signed non-sliding 24-hour `session_started_at` deadline.
- Client/server refresh after 56 real-time minutes and retry transient errors only through the last four minutes. Terminal failure logs a client out after networking/scene teardown or exits the dedicated server for supervised restart. Tokens never enter logs or Netcode.
- Before connection, owned reads/tickets use explicit `CharacterId`; ticket redemption binds one selected character to opaque `PlayerSessionId`. After redemption, delegated gameplay contracts use that session-selected character and must not accept another character ID.
- Admission uses a 60-second random single-use ticket and NGO Connection Approval. The authenticated server registers one Direct/Relay game session with a renewable 90-second lease. Gameplay RPCs carry no JWT/session credential; server-to-API calls carry server JWT plus `PlayerSessionId`.
- In-memory session/ticket storage supports one API process; use a shared atomic store before horizontal scaling.
- Async work owned by a spawned `NetworkBehaviour` uses a token tied to that network-spawn lifetime, cancels on despawn/destroy, and rechecks the same lifetime plus `IsSpawned` after every await before RPC/state mutation. Once an inventory mutation enters trade tracking, its API request and persistence continuation use the server-lifetime token; only the later RPC/UI continuation uses the spawn token.

## Persistence And Gameplay Invariants
- Equipment transitions attach the trusted server-calculated CharacterUpdate to CharacterInventories POST. Inventory and equipment/stats persist together in one EF SaveChanges; full inventory persists neither. NGO does not serialize CharacterUpdate from clients. Hideout result delivery depends on player spawn lifetime, not current room; only room visuals depend on instance identity.
- Hideout definitions reuse CraftingRecipeRequirement JSON in HideoutBuildingTypes. CharacterHideouts has a unique character/building key, BuildStartedAt and BuildEndsAt calculated with TimeProvider at acceptance; completion is derived from time with no completion write. Session-bound Hideouts POST reads or atomically consumes catalog materials, updates active Collect progress and inserts construction in one EF save. Unity joins the existing trade mutation barrier and quest semaphore; accepted persistence survives player despawn. Re-entry waits for preceding tracked writes before restoring the room.
- Account stash uses `CharacterStashes.ApplicationUserId` as FK/PK, with Count=64 and the existing InventoryState JSON conversion. Empty accounts read as 64 vacant slots without a row until first mutation. `CharacterStashes` server-session POST accepts read/deposit/withdraw/move/split; source slot/type/count and stash revision must match. Transfers remove the exact source slot only when the entire stack fits (automatic stack filling for right-click; empty/compatible selected slot for drag). Inventory, stash revision and Collect progress save together; EF inventory/revision concurrency checks prevent lost updates. Failed/uncertain operations never optimistically remove items or replay a transfer: the player reopens for an authoritative read. Tracked persistence uses server lifetime and the per-character quest semaphore, while RPC/UI continuations are guarded by spawn lifetime.
- Never assume character ID `1` or one character per user. `UserManager.Characters` is keyed by Netcode client ID; temporary first-character selection stays isolated until a real selector exists.
- Inventory positions are stable: `None` with count `0` is an empty slot; full removal clears rather than compacts. Each stack caps at `1024`.
- Inventory transactions clone state, remove first, then fill matching partial stacks and free slots. If all additions cannot fit, return `InventoryFull` and persist nothing. Unity may preflight for UX, but API remains authoritative.
- Persisted oversized legacy stacks normalize without item loss, reusing empty slots before extending effective capacity.
- CharacterInventory uses a separate numeric Revision for EF concurrency, advanced by ApplicationDbContext on every modified inventory save. Normalized inventory JSON is not a concurrency token, so legacy JSON remains writable. Migration AddCharacterInventoryRevision adds the column with zero for existing rows.
- Compound gameplay transitions have one persistence owner. Collect-quest completion removes requirements, persists the Main EXP reward, and completes the quest in one API save; Unity only synchronizes the result.
- Kill quest progress is additive. Collect progress is the absolute persisted inventory count, initialized on acceptance and resynchronized after every add/remove; it may regress Finished -> Accepted.
- Queued Collect progress captures the bound player session before waiting for the quest semaphore and persists all matching quests under the server lifetime after despawn; only owner RPC delivery depends on the original spawn lifetime.
- Disconnect revocation waits for both pending trade commits and tracked inventory/quest mutations, preserving delegated credentials until accepted persistence settles.
- Player-session revocation retries under the server lifetime until confirmed, using exponential delays capped at 30 seconds. A transient API failure must not strand the character behind the single-active-session check.
- Health potions attach Health to the same inventory transaction that removes one potion. The item-state gate serializes them with gear/ammo, and server healing is applied only after persistence succeeds; rejected requests resynchronize the predicted client state. An uncertain potion result disconnects the owner for authoritative restoration on reconnect instead of guessing whether consumption committed.
- Damage remains immediate, but HP persistence shares the item-state gate with potions/gear/ammo and reads current HP only after acquiring it. Successful potion persistence applies healing to its captured server character before releasing that gate, including after despawn; subsequent queued damage saves therefore include that healing. Owner notifications still require the original spawn lifetime.
- Quest accept/progress/complete operations serialize through one per-character semaphore. Completion RPCs send only the character-quest ID; the authenticated API resolves and returns the authoritative quest ID. Every completion conservatively joins the inventory-mutation barrier because only that authoritative result can determine whether Collect items were removed.
- Trade negotiation is ephemeral Unity-server state: one invitation/session per player, normalized bilateral offers, per-side lock, both-side confirmation, and an uneditable/uncancellable committing state. Lock/commit reserves inventory from other mutation paths.
- Trade commit sends one immutable snapshot to `CharacterInventories/Trade`. The trade GUID is an idempotency key; the API atomically saves both inventories, active Collect progress derived from both post-trade inventories, and a payload-fingerprint receipt. It removes both outgoing sides before fitting incoming items with normal capacity rules. EF concurrency loss, invalid items, or capacity failure changes neither inventory nor quest progress; an exact retry returns `Applied` without duplication. Quest completion and inventory-dependent Collect acceptance/progress join the inventory-mutation barrier: locking blocks new operations, and commit waits for tracked writes that started before the lock. Once tracked, the persistence/semaphore portion uses the server-lifetime cancellation token so participant despawn cannot release the barrier early; any RPC/UI continuation remains guarded by the spawned component's network-lifetime token. A server-lifetime coordinator, not either participant's spawned component, owns the immutable commit/retry across player despawns and cancels on server shutdown. Only uncertain transport/server failures retry; a disconnect delays delegated-session revocation until the pending commit resolves.
- After any uncertain commit response, the Unity server may query server-only `CharacterInventories/Trade/Resolve` by trade GUID. A durable receipt returns current authoritative snapshots without requiring the now-ephemeral player session; a later definitive rejection is safe to release only when receipt resolution confirms `ReceiptNotFound`.
- Receipt resolution also precedes business-status rejection of a retried commit after an uncertain outcome. Applied receipts deliver the authoritative snapshots; failed/unavailable resolution keeps the same offer reserved and retries.
- A successful trade response or receipt lookup includes authoritative snapshots of both inventories. The Unity server associates each snapshot with a participant by authenticated character ID, not by trusting source/target response position. A completion RPC first closes the trade projection, then replaces local inventory and starts one authoritative post-commit GET; `InventoryManager` generations prevent older loads or mutations from overwriting either state.
- The six-type trade-offer cap is an explicit review/abuse bound on accepted ephemeral state, not an inventory, max-stack, or atomic-transaction limitation. A seventh raw offer entry is rejected before duplicate item types are aggregated, bounding request processing as well as retained state.
- Party state is ephemeral and friend-authorized. Leader rules and disconnect cleanup are server-owned. Enemy rewards use the dead enemy as center, always include the authenticated killer, include connected party members within the current 1000-unit radius, split Main EXP by integer division, and grant personal loot plus Kill credit to each eligible member.
- Party reward range uses the moving Player child, not the stationary NetworkObject root, including offset dungeon instances.
- Crafting recipes are typed Domain definitions and returned/displayed by recipe ID. Active client crafting cancels on movement, actual damage, panel replacement/closure, Escape, or leaving station range; server-side recipe/material/station hardening remains open.

## Character, Gear, Ammo, And Consumables
- `UpdateCharacterCommand` persists optional health/max health, six stats, and equipment fields exactly as supplied by the authoritative server.
- Current stat mechanics are percentage based: sword/Strength, wand/Intellect, bow/Dexterity scale outgoing weapon damage; Dexterity is capped dodge, Speed scales movement, and Armor is capped reduction. Animator root motion remains disabled; `ThirdPersonController` drives movement.
- Gear behavior uses `AbstractUsableItem`/`AbstractGearUsableItem`; `UsableItemFromEnum.Inventory` or `.Gear` specifies origin. Metadata supplies stat bonuses and `InventoryItemEnum.IsWeapon()` classifies weapons.
- Ammo contract is `AmmoType + AmmoCount`; compatibility comes solely from `InventoryItemParametersAttribute.WeaponCategory`: Arrow/Bow, Rune/Wand, Feather+Oil/Sword. Equip/merge/swap/unequip and incompatible-weapon auto-unequip preserve whole stacks and bonuses.
- Feather is consumed after a positive non-dodged incoming hit; Arrow/Rune/Oil after outgoing damage calculation. The final unit affects that hit, then removes its bonus and resets the slot to template.
- Health potions heal at most 20 and are not consumed at full health. Strength/Speed potions apply server-authoritative runtime-only `+20` for 60 seconds; reuse refreshes duration and disconnect/expiry clears it.

## Unity UI And Interaction
- HideoutScene reuses DungeonTravel instancing/visibility but selects rooms by authenticated character ID and ignores party reconciliation. Hideout rooms remain loaded while their owner is connected, including in other scenes, so construction and respawning continue. Disconnect releases the room; re-entry restores timestamps. The authoritative building snapshot travels in the scene preparation message and is applied before arrival, independently of NetworkVariable delivery order. Farm uses CraftingCanvas and InventorySlot for construction, timed upgrades and six crop/seed mappings (2/4/6 active slots). CharacterHideouts.Data persists Farm level, upgrade deadline, seed stacks and per-slot ready product/deadline; a separate row Revision avoids JSON-normalization concurrency issues. One seed is consumed when a crop matures; ready crops wait for atomic harvest into inventory, and offline elapsed time reconciles on read. Server-controlled Spawners project durable ready crops without autonomous replenishment. Their serialized intervals remain 5 seconds for testing. Travel snapshots include all room buildings. The portal hover/range path, ghost materials and API-time countdown remain shared. Development database reset still deletes Hideout state; see `Client/Automation/hideout-smoke.md` for pending authenticated coverage.
- Dungeon design rationale and PoE/WoW/New World comparison: `Client/Automation/dungeon-design.md`. The minimal shared-run model intentionally retains immediate last-exit cleanup and party-leaver return. Party reconciliation is event-driven, repeated after arrival to cover changes during loading; only failed persistence schedules a delayed retry. Travel uses one `TravelStage` enum rather than independent phase flags.
- Entrance and exit use the same `Prefabs/DungeonPortal.prefab`, translucent violet material and explicit Arrival transforms. Arrival resets controller velocity and informs Cinemachine of the teleport; the persistent LoadingScene scope renders before room changes and stays visible through camera evaluation.
- Dungeon portals use the shared pointer cursor and right-click within 5 units, with server-side session, alive-character, range and trade checks. `DungeonTravel` keeps the player/connection alive and loads/unloads `DungeonScene` additively under the existing `LoadingScene` scope; Main/UI/audio and LoadingScene remain loaded; the previous environment is unloaded before the destination environment loads. EnvironmentScene owns the former TestScene NPC/crafting roots and ServerScene spawners; those separate scenes were removed. The dedicated server retains EnvironmentScene for world players and creates separate instance scenes with copies of `Prefabs/Locations/Resources/DungeonEnvironmentPrefab` at separated coordinates. Each copy registers the prefab's baked NavMeshSurface; there is no runtime baking. LocationEnvironment retains navigation validation and return-portal arrival lookup, including TemplateScene. Bean creation belongs to Spawner: Maintain Population defaults to true for world spawners; DungeonEnvironmentPrefab contains BeanSpawner (one Bean) and ChamomileSpawner (one chamomile) with replenishment disabled. Instance identity and position are assigned before network spawn. Empty-instance cleanup stops spawners and destroys active/pooled objects; a new instance receives fresh populations. Scene overrides must be applied to the shared environment prefab before rebuilding the server, because server instances are created from that prefab rather than the client scene. `DungeonWorldObject` installs NGO observer filtering before spawn, including late joiners, and gameplay checks compare instance identity for combat, rewards, gathering and trade. NGO integrated scene management is disabled in MainScene and the shared session setup: environments are client-specific and all gameplay NetworkObjects are dynamically spawned, so global scene synchronization must not reload another player's environment. Temporary rooms are not globally broadcast NGO scene loads.
- Portals serialize `LocationEnum` (EnvironmentScene=0, DungeonScene=1, TemplateScene=2) as the destination. Clients send that enum, and the server resolves the matching portal (one portal per destination in a location) in the current location/instance and validates range/session/trade rules. No separate PortalId is needed. Instance lookup uses both stable party identity and destination location. Additional instanced locations follow the `<Name>Scene` / `Prefabs/Locations/Resources/<Name>EnvironmentPrefab` naming convention, with `LocationEnvironment`, a return portal and baked NavMeshSurface.
- Each ephemeral party has a stable GUID independent of its leader. Members enter individually and join its current run. Solo runs are separate; forming a party can adopt a solo run if the party has no other run. Leaving a party immediately removes visibility/interaction eligibility and returns that member through loading; joining a party with an existing run returns a solo entrant to the world first. Killing the Bean marks completion without respawning it or ejecting players. The last departure/disconnect releases the room; the next entrance creates a fresh run.
- `CharacterTransform.SceneName` in API/Unity DTOs identifies the resumable location (currently `EnvironmentScene`). Before dungeon travel, serialized server saves durably record the portal's world return point; periodic saves inside a dungeon keep that point, never the room offset or ephemeral instance ID. Reconnect therefore starts outside. The live scene is synchronized by `DungeonTravel`; travel uses ordered save/load/ready/arrival stages with a transition ID, duplicate-ack guards, a 45-second timeout and spawn-lifetime checks. Changing location cancels uncommitted trade, while accepted trade commits retain their existing server-lifetime owner.
- `ActionBarsUI` is scene-backed in `UIScene` and uses ten `ActionBarSlot` variants of `InventorySlot`, ordered 1–0. Inventory drag assigns an item type without moving/consuming it; right-click/digit uses the existing inventory subscription, left-click does nothing, and dragging outside the whole bar clears the binding. Action-bar drag reuses the shared inventory preview and cancellation; dropping on another slot moves the binding (swapping occupied slots); dropping on the same slot or in a gap preserves it. InventorySlot count text auto-sizes within its inset rectangle (10–22), inherited by ActionBars, so full counts fit smaller inventory cells. All currently usable items, including gold, potions, gear and ammunition, are supported. Slots are 64 canvas units (previously 50), with bottom-center anchors. Bindings survive empty stacks; counts reflect current inventory. Typing, active dragging, trade and an open merchant suppress use (merchant's shared subscription otherwise sells items). Narrow layouts use five columns and leave room for Quick Access.
- `CharacterSettings` has one row per character (character FK/PK), auditable modification time, language and a JSON array of exactly ten item enum values (`None` means empty). Client-authorized GET/POST verify ownership independently of gameplay sessions; settings never grant inventory or gameplay authority. The migration backfills existing account languages and empty bindings; missing rows return account-language defaults and are created on save. Client startup loads selected-character settings before quests/UI, serializes complete binding snapshots, and displays edits immediately. Save responses update only the confirmed snapshot; a failed latest edit rolls the display back without undoing newer edits. Source drag restoration and optimistic refresh happen before yielding, avoiding the removal flash. Language survives token refresh, invalidates the translation cache on change and travels in `Accept-Language` for localized API reads; account language remains the pre-selection default.
- Prefer scene-backed reusable prefabs. `*UI.cs` resolves/caches owned hierarchy controls during startup; serialize only external assets/configuration. Dynamic repeated entries instantiate prefabs rather than constructing hierarchies ad hoc.
- Every modified UI must be responsive: explicit CanvasScaler, suitable anchors/layout groups, bounded preferred sizes, narrow-screen margins, and landscape plus portrait/narrow validation.
- Static prefab/scene text uses `TranslateUI`; dynamic/stateful/formatted text uses `TranslateManager`. Append `TranslateKeyEnum` and matching client/API localization entries only at the end and in identical order.
- A focused `TMP_InputField` exclusively owns keyboard input through `InputFocusUI`; gameplay controls and shortcuts remain neutral while typing.
- `LoadingScene` remains loaded on clients and owns nestable disposable `LoadingScreenUI` scopes. Bootstrap owns orchestration; scene-scoped `LoginUI` owns login view behavior. Dedicated builds remain Bootstrap-first.
- Shared inventory drag uses a non-raycastable cursor preview and source placeholder; cleanup restores source visuals. Inventory/Gear swaps and merges use existing authoritative paths; Loot and Merchant reuse the same drag lifecycle and their existing pickup/purchase/sale subscriptions.
- Hover/item descriptions use `InventoryUI.PrepareDescription`; preview Canvas order is 20, above normal gameplay UI. Quick Access and Buff UI are scene-backed and reuse `InventorySlot` presentation.
- Trade uses prefab-authored invitation/session/action rows, masked scroll views, and a `TradeOfferSlot` variant. Offer fields share the label inset; offers use exactly four left-aligned columns with symmetric padding, responsive square cells, and inset icon artwork. Trade placement accounts for visible Inventory, Loot, and Log bounds and only shifts around Loot on a real rectangle collision; it prefers sufficient room to the right of Loot and otherwise chooses the best-scaled non-overlapping side. Log messages wrap at preferred height on non-blocking sorting order 30.
- `TradeInventoryProjection` visually subtracts active/pending offered quantities from exact source slots without mutating authoritative DTOs. Rejection/removal/closure restores them; unrelated peer snapshots must not clear a pending offer. Local offer mutations are single-flight. Reserved source/target slots reject index moves.
- Own-offer drag reuses InventoryUI preview/restoration, forwards wheel scrolling, and clears `eligibleForClick` so a completed drag cannot also trigger click removal. Competing panels wait for authoritative trade closure; never optimistically cancel a committing transfer.

## Coding And Operational Conventions
- Keep code simple and consistent with surrounding style. Separate logical stages with blank lines; keep assignment targets with their expressions; extract locals instead of awkward wrapping.
- In LINQ, put independent filters in separate `.Where(...)` calls and use `x` for generic lambda parameters. Keep the source on the first line and every chained operation, including terminal selectors/materializers, on its own indented line. Add a blank line between independent queries and subsequent derived local declarations.
- Sensitive request `ToString()` implementations omit secrets entirely. MediatR pipeline logging handles request start/completion/timing/rejection/failure; use injected `ILogger<T>` only for meaningful business/audit events.
- New or modified logic in the API, Unity client, and Unity dedicated server must include meaningful diagnostic logs that support later error analysis. Cover important operation stages, state changes, rejections, retries, and failures with enough safe context (operation name, relevant entity/correlation IDs, outcome, and exception details) to reconstruct the flow across components. Reuse existing logging mechanisms, choose appropriate severity levels, avoid duplicate or per-frame noise, and never log passwords, tokens, or other secrets. Keep Domain entities I/O-free by logging at the coordinating boundary.
- Preserve Unity `.meta` files and avoid generated/cache outputs. Keep mirrored enums/contracts/localization synchronized.
- After API source/config/contract/migration changes, rebuild and restart the API before runtime verification; earlier binaries are not evidence for the current diff.
- Dev automation and Unity menu behavior must stay aligned. Persist per-process runtime logs under ignored `Client/Logs/Runtime`; keep build logs separate.

- TemplateScene uses TemplateEnvironmentPrefab with a baked TemplateNavMesh, a floor and a return portal but no enemy or walls. The same instance/party lifecycle handles both side locations; enemy spawning is optional. Portal standing poses come from their Arrival child, approximately 1.5 units from the center and facing away from the portal. Designers can move/rotate Arrival without changing code.

- Admission permits only one active player session per character across game servers; Redeem enforces uniqueness under the ticket lock and normal revocation releases it. Ammo persistence and equipment changes share a per-player semaphore so older ammo snapshots cannot overwrite later equipment transactions.
- Accepted ammo consumption captures the character and bound session before waiting for that semaphore. It finishes decrement/stat removal and persistence after despawn using the captured character; only owner RPC delivery is spawn-bound. A live character replaced by equipment recovery is used when the same spawn is still active.

- During current development, target the current hideout JSON format only; do not add legacy format adapters without an actual compatibility requirement.
